# CTC-to-agent provenance transport research

## Finding

Use Firefox extension-to-extension messaging for the primary design. Keep routing and receipt creation inside CTC. Let the already-required firefox-cli extension request a short-lived receipt through CTC's external-message handler. Keep tab listing and verification on the public `firefox-cli` surface.

This adds no browser, daemon, native-host registration, CTC permission, or local network listener. It does require a small CTC API and a companion firefox-cli extension/protocol feature; the current CLI has no receipt command. A receipt should identify the CTC-created tab and include source/replacement IDs, URL, container ID, timestamp, and expiry. The wrapper still checks the live tab and container through `firefox-cli`.

CTC creates the replacement with `tabs.create`, then removes the source tab ([CTC source](https://github.com/kaushikgopal/ff-container-traffic-control/blob/5c4227c/src/background.js#L274-L291)). Firefox supports `runtime.sendMessage(extensionId, message)` and CTC can check `sender.id` in `runtime.onMessageExternal` ([MDN external messages](https://developer.mozilla.org/en-US/docs/Mozilla/Add-ons/WebExtensions/API/runtime/onMessageExternal)). Firefox allows extension-to-extension messages by default when `externally_connectable` is absent ([MDN manifest key](https://developer.mozilla.org/en-US/docs/Mozilla/Add-ons/WebExtensions/manifest.json/externally_connectable)). CTC should accept only the exact firefox-cli ID, `ff-cli-bridge@respawn.pro`, and validate a narrow request schema. Do not trust a caller-supplied ID.

## Transport comparison

| Option | Fit, setup, and threats |
| --- | --- |
| **External extension message** | Best fit. Firefox supplies `sender.id`; CTC checks it. The local CLI already reaches firefox-cli through its native host and authenticated local IPC. This does not authenticate arbitrary local processes at CTC; the trusted boundary is the installed firefox-cli extension. Risks include a compromised/updated companion extension, ID/version drift, and stale or replayed receipts. Use expiry, request correlation, bounded storage, and live-tab verification. macOS adds no setup beyond the already-required CLI extension/native-host install. |
| **Native messaging helper + local rendezvous** | Strong browser-to-helper gate, but more moving parts. CTC needs `nativeMessaging`, a fixed Gecko ID, and a registered native manifest whose `allowed_extensions` includes CTC. Firefox checks that allowlist and passes the manifest path plus caller add-on ID as process arguments ([MDN native messaging](https://developer.mozilla.org/en-US/docs/Mozilla/Add-ons/WebExtensions/Native_messaging), [native manifests](https://developer.mozilla.org/en-US/docs/Mozilla/Add-ons/WebExtensions/Native_manifests)). The helper can verify that Firefox-supplied argument. Firefox does **not** make a helper “accept only CTC” by default: the manifest allowlist and helper's own caller check define that boundary. The current firefox-cli host allowlists and expects only `ff-cli-bridge@respawn.pro` ([manifest generator](https://github.com/respawn-llc/firefox-cli/blob/c118396/packages/native-host/src/native-manifest.ts), [launch check](https://github.com/respawn-llc/firefox-cli/blob/c118396/packages/native-host/src/host-launch.ts#L27-L67)); it cannot be reused unchanged. One helper binary/manifest could allow both IDs, but must branch on Firefox's caller argument and add a CTC receipt route. CTC can use `sendNativeMessage` for a one-shot write; `connectNative` keeps the helper alive only while its port/page remains open. A local socket needs restrictive per-user permissions and authentication; firefox-cli already uses a per-user token, but same-user malware can usually read it ([IPC auth](https://github.com/respawn-llc/firefox-cli/blob/c118396/packages/native-host/src/local-ipc-auth.ts#L12-L47)). On macOS, setup must install or update a manifest under `~/Library/Application Support/Mozilla/NativeMessagingHosts/`; CLI setup already handles its own manifest. CTC must not silently require this extra native installation. |
| **Loopback server** | Poor fit. Requires a persistent local server, port discovery, authentication, lifecycle management, and CTC fetch/host-permission decisions. A localhost endpoint also faces cross-origin request and DNS-rebinding/CSRF risks. macOS needs a separately installed or launched service. This is more setup and attack surface than the existing CLI host. |
| **File/download receipt** | Possible but brittle. CTC currently lacks the `downloads` permission; it would need to create a receipt file and the agent would need a known download path and safe freshness/correlation checks. Paths depend on Firefox settings, and users can move, overwrite, or replay files. Existing CTC export is rules-only JSON shown in a read-only text field for manual copy; it is not a navigation receipt ([export code](https://github.com/kaushikgopal/ff-container-traffic-control/blob/5c4227c/src/options.js#L542-L570)). No additional setup for export, but it cannot prove a tab's origin. |
| **Before/after snapshots + human confirmation** | Best zero-change baseline. Compare public `firefox-cli tab --json` results and ask the user to confirm the intended new tab before acting. The CLI exposes `cookieStoreId` as optional ([tab schema](https://github.com/respawn-llc/firefox-cli/blob/c118396/packages/protocol/src/target.ts#L3-L15)). This confirms observed state, not CTC provenance. Concurrent tabs, redirects, missing container data, and timing can make the match ambiguous; stop rather than infer. |

## Extension-page API check

A stable optional CTC API is feasible as an extension message contract, not as a page the CLI drives. `firefox-cli eval` runs in a tab's page main world, while Firefox disallows script injection into extension pages ([CLI command docs](https://github.com/respawn-llc/firefox-cli/blob/c118396/docs/commands.md#eval-screenshot-and-batch), [MDN executeScript](https://developer.mozilla.org/en-US/docs/Mozilla/Add-ons/WebExtensions/API/scripting/executeScript)). A `moz-extension://` UUID is profile-specific, not a stable URL ([MDN web-accessible resources](https://developer.mozilla.org/en-US/docs/Mozilla/Add-ons/WebExtensions/manifest.json/web_accessible_resources)). Exposing a CTC options page therefore adds a fragile bridge and does not provide the needed CLI access. Use a versioned, read-only external-message request instead.

## Unresolved live probes

- Confirm Firefox allows the installed CTC and firefox-cli extensions to message each other; verify CTC receives the expected `sender.id`.
- Verify receipt availability across CTC background suspension and navigation races; verify expiry and tab-ID reuse handling.
- Confirm the public CLI returns the live replacement URL and `cookieStoreId` after redirects. Treat absent container data as unknown.
- If native messaging remains under consideration, test caller arguments, allowlist behavior, and whether the existing host can support concurrent extension connections without changing its CLI pairing path.

## Decision

Prefer external messaging for provenance. Use human confirmation when upstream extension work is out of scope. Do not add a loopback service or file/download path unless live probes show extension messaging cannot meet the required lifecycle.
